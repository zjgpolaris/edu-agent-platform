successful push CI run and is deployed by the production service. Database,
authentication, migration 016 and rollout-observation writer checks are healthy.

Production execution is still blocked:

- The AutoTutor Production Verification workflow has no runs.
- Repository Actions variables and secrets are empty.
- No required workflow receipt, schema-v4 final evidence or rollback verification

- v1.50 entry therefore remains `NO_GO`.

v1.49.7 also leaves one code-level trust gap. The service considers any
well-formed configured bootstrap digest “attested”, but the calling workflow
does not present that digest. A machine token proves possession of the API
credential, not that the request came from the Environment whose controls were
reviewed.

## 2. Goal

Cryptographically bind every machine-authenticated AutoTutor production
verification request to the same reviewed bootstrap attestation configured in
both GitHub Environment and Render, and carry the public attestation reference
through the sealed workflow receipt.

This makes the repository development-complete for the production ceremony. It
does not execute or claim completion of the external ceremony.

## 3. Non-goals

- Do not create or edit GitHub Environments, variables, secrets or reviewers.
- Do not write Render settings.
- Do not enable Canary traffic or execute drills.
- Do not claim Production Verified without real workflow artifacts.
- Do not enter v1.50, delete Legacy, disable comparator or exceed 1% traffic.
- Do not repair unrelated global LLM capability/evidence readiness.
- Do not add a database migration.

## 4. Binding contract

### 4.1 Configuration

The reviewed bootstrap attestation generated by
`scripts/verify_autotutor_verification_environment.py` has a 64-character
lowercase `attestation_sha256`.

Operators configure exactly that public digest in two places:

- GitHub Environment variable
  `AUTOTUTOR_PRODUCTION_BOOTSTRAP_SHA256`.
- Render variable
  `EDU_AGENT_AUTOTUTOR_VERIFICATION_BOOTSTRAP_SHA256`.

The raw machine token remains only in the GitHub Environment secret
`AUTOTUTOR_PRODUCTION_API_TOKEN`; the token digest remains only in Render.

### 4.2 Request proof

The workflow sends the Environment digest in:

```text
X-AutoTutor-Bootstrap-SHA256: <64 lowercase hex>
```

For a machine token, the server must:

1. validate the header shape;
2. compare it with the Render digest using constant-time comparison;
3. reject missing, malformed or mismatched proof with 403 and stable detail
   `bootstrap_attestation_invalid`;
4. emit a safe authentication-failure audit event without either digest.

A normal admin JWT remains compatible and does not require this machine-only
proof. Authentication-disabled local development remains compatible.

### 4.3 Scope

The proof applies to the same four least-privilege endpoints introduced in
v1.49.7. Other admin endpoints continue rejecting the machine token.

## 5. CLI and workflow contract

`scripts/verify_autotutor_canary_deployment.py` reads the public digest from
`API_BOOTSTRAP_SHA256`, validates it before network access and attaches it to
verification/snapshot requests.

The evidence persistence client and the two direct evidence reads in the
workflow attach the same header. This prevents the preflight from being bound
while candidate/final persistence silently bypasses the binding.

The GitHub workflow reads only:

```text
vars.AUTOTUTOR_PRODUCTION_BOOTSTRAP_SHA256
```

It never reads the bootstrap reference from a secret and never derives it from
the API token.

## 6. Receipt contract

Upgrade the production verification receipt to schema version 2 and add:

```json
{
  "bootstrap_attestation_sha256": "<64 lowercase hex or null>"
}
```

The bootstrap digest is a public integrity reference, not a credential. It may
appear in the PII-free receipt and artifact, but never in application API
responses or audit metadata.

The field is covered by the existing canonical receipt seal. Modifying or
removing it invalidates `receipt_sha256`.

CI-blocked receipts also use schema v2 and include a validated reference or
`null`, ensuring one receipt schema across every workflow outcome.

## 8. Deterministic verification

Tests must prove:

1. Current and next machine tokens require the matching attestation header.
2. Missing, malformed and mismatched headers receive 403.
3. Admin JWT remains accepted without the header.
4. Unrelated admin endpoints still reject the machine token.
5. Remote verification requests carry the expected header.
6. Evidence POST and evidence GET workflow paths carry the same header.
7. CLI fails before network access when the bootstrap variable is missing or
   malformed.
8. Receipt schema v2 includes the public digest and its canonical seal changes
   after tampering.
9. Workflow uses an Environment variable, not a secret, for the digest.
10. Existing AutoTutor production, rollback and privacy suites remain green.

## 9. Acceptance criteria

- Spec, implementation, runbook and deterministic tests are committed together.
- `python scripts/release_gate.py --fast` passes.
- `git diff --check` passes.
- No raw token, real digest or external credential is committed.
- No external production state is mutated by development or tests.

## 10. Post-deployment ceremony

After deployment, an authorized operator must:

1. Create the protected `production-verification` Environment.
2. Configure API base and raw machine token.
3. Run and review the bootstrap checker.
4. Configure the same attestation digest in GitHub and Render.
5. Configure only the raw token digest in Render and redeploy.
6. Run preflight, control snapshot, manually approved 1% Canary snapshot and
   rollback verification in order.
7. Preserve the schema-v2 receipts and schema-v4 final GO evidence.
8. Confirm `v150_entry_ready=true` before drafting v1.50.

Development Complete is not Production Verified. Only real Environment controls,
production observations and immutable workflow evidence can satisfy the latter.
